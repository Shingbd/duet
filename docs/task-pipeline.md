# 任务 → 节点的开发与审核流程

状态：目标设计，尚未完整实现；不是现有 AI 总结格式的包装。

## 用户交互
用户提交的一整个需求称为任务；AI 拆分出的完整执行单元称为节点。术语、状态和已确认布局见 docs/nodes.md。
AI 生成结构化节点计划，再按依赖顺序逐个执行。每个节点完成后单独进入待审；选中节点后只显示该节点的新增、修改、删除文件与逐文件 diff。
背景代码放在项目视图，不混入审核文件列表。不以“待审 · 文件名”追加第二套文件。
任务到达不抢正在阅读的版本、焦点或滚动位置。

## 契约
任务记录原始需求、总体目标、约束和验收条件。
节点记录稳定 ID、标题、目标、文件/模块范围与边界、实现方法、约束、依赖节点 ID 与可检查的验收条件。
AI 拆分应返回可解析结构，而不是仅在聊天里列出清单。主机校验必填项、唯一 ID、依赖有效性、无依赖环、任务数量上限及完整状态。
权限仍须明确授权；契约不是操作系统沙箱，也不等于用户已批准生成代码。
现有独立工作区中“结构化任务契约”的 AI 候选实现尚未验证/集成，不当作这套调度已完成。

## 执行与固定版本
规划阶段使用只读工具，不能一边规划一边随意写代码。
执行每个子任务时仅传入当前子任务契约和必要上下文，固定基线版本。
完成事件须等待 agent_settled，原始消息、工具日志和错误记录可追溯。
子任务 k 的差异必须相对它的执行前基线，不能全部相对父需求起始 HEAD；否则后一个任务会错误包含前一个任务的文件。
将开始版本、完成检查点、变更文件与验收状态绑定到该子任务，保存后发布待审。
接入真实待审任务背压；超过积压限额时在子任务边界暂停，不继续制造未审阅工作。
控制时间/调用预算；暂停、纠正与取消保持现有显式语义，不在崩溃或重启后自动重跑。

## 审核
任务卡片分别显示：规划、运行、实现完成/待审、未验证/通过/失败、批准/要求返工。
AI 执行结束只能意味着实现阶段停止，不意味着验收通过或用户批准。
验收条件默认“未验证”；只有绑定到确切版本的 Runner 证据或明确人工核验才能改变验证状态。
一个任务的返工不能覆盖其旧检查点；新版本要求重新审核。
审批和最终合并独立处理，不因 m 标记已读而隐式放行。

## 数据与恢复
需要新增父需求、子任务契约、依赖、执行尝试、固定检查点、验收证据及人工反馈记录，明确 schema 迁移。
重启恢复任务树、各任务状态和阅读版本；未完成执行标记中断，恢复操作须明确确认。
保存任务 ID + 版本 + 文件路径的阅读位置，而不是以显示名称充当任务身份。

## 实施顺序
1. 契约与计划 schema、模型规划输出解析和校验。
2. 顺序子任务调度、每阶段基线/检查点、真实背压与中断控制。
3. 按子任务分组的待审列表、当前任务文件/diff、重启恢复。
4. 验证 Runner、逐条验收证据、结构化返工与版本审批/合并。

当前已完成的前置修正：最近任务审核侧栏只显示变更文件，Git 风格颜色/状态，逐文件固定 diff；此前单任务链路、持久化与暂停/纠正继续沿用。
