# 任务与节点

本设计已获用户确认。先实现领域模型、持久化和执行，再切换布局；下述目标不代表已有功能全部交付。

## 定义
- 任务（Task）：用户提交的完整需求。保存原始需求、总体目标、约束、验收条件和历史对话。
- 节点（Node）：AI 拆分出的有明确边界的执行单元。必须包含稳定 ID、标题、目标、范围/边界、实现方法、约束、依赖节点和验收条件。
- AI 的结构化计划需由宿主校验。缺字段、重复 ID、不存在的依赖、依赖环不能进入执行，不将聊天中的清单冒充节点。
- 实现方法可调整；扩大范围、修改约束/验收条件需要明确记录或重新规划，不能静默放宽。

## 状态与版本
节点执行状态、验收状态、人工审核状态互相独立。
实现结束只记作待审，验收默认未验证；AI 自述测试通过不改变验收状态。
每次执行绑定开始版本与完成检查点。节点差异相对该次执行的开始版本，而非全部相对最初 HEAD。
返工保留旧执行记录及固定检查点，新版本不继承旧批准。
依赖按实现顺序调度不等于前置节点已获批准；依赖候选代码最终仍需整体验证与人工审核。
暂停、取消、时间预算和待审积压限制适用于整个任务。重启只恢复记录，不自行继续模型调用。
节点文件范围是可检查的契约，不是 OS 沙箱；越界变更必须显式报告。

## 交互布局
1. 任务：左侧历史任务与节点树，正文显示任务对话或所选节点契约/状态。不要显示项目文件或待审文件。
2. 审核：左侧待审节点，展开所选节点的变更文件；正文显示固定逐文件 diff、验收状态和反馈。只显示选中节点的文件。
3. 项目：文件树与背景代码。
4. 知识：人工笔记，保留现有行为。
到达新节点不抢走已选节点、固定文件版本、焦点或滚动。
m 始终仅表示已读，不是批准；审批必须明确，且绑定检查点。

## 分步实现
1. Task/Node/Plan 领域模型、JSON 校验与依赖排序；SQLite 迁移、旧任务兼容和中断恢复。
2. 只读模型规划、节点顺序执行、阶段检查点、真实待审背压，保留暂停/纠正/取消。
3. 历史任务/节点导航与按节点筛选的审核布局，保留当前阅读版本及位置。
4. 后续独立接入验证 Runner、验收证据和受控合并；本轮不自动运行测试、合并或部署。
